# Research process

How we iterate on the chameleon's trading strategy. The point is to make every change deliberate and reviewable, not to chase backtest scores.

## The loop

```
  strategies/strategy_vN.md  ──►  analysis_scripts/analysis_vN.py  ──►  results/analysis_report_vN.md
                                                                              │
                                                                              ▼
                                                                analysis_scripts/postmortem_vN.py
                                                                              │
                                                                              ▼
                                                                  results/postmortem_report_vN.md
                                                                              │
                                                                              ▼  (human reads, decides)
                                                                     strategies/strategy_v(N+1).md
```

One full lap = one strategy revision. No step is automated end-to-end — a human reads the postmortem and writes the next spec by hand.

## Folder layout (enforced)

All research artifacts live under `analysis/`:

```
analysis/
├── strategies/                 # specs — strategy_vN.md, one per version (immutable once reported on)
├── analysis_scripts/
│   ├── common.py               # shared infrastructure (no suffix)
│   ├── analysis_vN.py          # per-version: runs the spec
│   └── postmortem_vN.py        # per-version: diagnoses the run
├── data/                       # shared inputs (no suffix) — btc_hourly.csv, btc_funding.csv
├── output/                     # per-version artifacts — equity_curves_vN.png, action_log_vN.csv, postmortem_attribution_vN.png
└── results/                    # per-version reports — analysis_report_vN.md, postmortem_report_vN.md
```

**Suffix convention.** Every per-version file is suffixed `_vN`. Shared code and shared data carry no suffix. Reports are **per-version files**, not overwritten each run — they're committed and kept.

**"Create the necessary files for vN" means**: read `analysis/strategies/strategy_vN.md`, generate `analysis_scripts/analysis_vN.py` and `analysis_scripts/postmortem_vN.py` that implement that spec, write outputs to the paths above. Reuse helpers in `common.py` (data loaders, signal functions, deposit calendar, control / B0 simulator, metrics, bootstrap CIs). Do **not** edit prior-version scripts or reports — they document earlier specs and are part of the audit trail.

## What each artifact is for

- **`analysis/strategies/strategy_vN.md`** — the spec we are *committing to* before we look at any results. Signals, policy table, overrides, action space, honest caveats. (v1 lives at `analysis/strategies/placeholder_strat.md` for historical reasons.)
- **`analysis/analysis_scripts/analysis_vN.py`** — runs the spec on cached data. Deterministic; same inputs → same outputs.
- **`analysis/results/analysis_report_vN.md`** — headline numbers (return, max DD, Sharpe/Sortino, trade count, time-in-market, action distribution). Generated by `analysis_vN.py`. The "what happened" artifact.
- **`analysis/analysis_scripts/postmortem_vN.py`** → **`analysis/results/postmortem_report_vN.md`** — the "why it happened" artifact. Per-policy-cell forward returns, counterfactual arms / experiment matrix, signal-quality CIs, cash drag, regime breakdown.

## When to iterate

Concrete triggers for writing a new `strategy_v(N+1).md`:

1. A signal-state mean forward return has a 95% CI that **excludes zero in the opposite direction** to the spec's assumption. (E.g. "Hot" funding was supposed to be contrarian-bearish but its CI is firmly positive.)
2. A **counterfactual arm dominates** the baseline on both return and max DD. The component it strips out is a candidate for removal.
3. A policy cell has **n < 5** decisions in-sample — we cannot conclude anything about it; either change the spec so it fires more, or accept it as untested.
4. The **drawdown profile** is unacceptable for the dashboard's stated purpose (the win condition is risk-adjusted, not raw return — `placeholder_strat.md` is explicit about this).

If none of the above is true, do *not* iterate. Noise is not a signal.

## Discipline

- **Don't tune to in-sample noise.** ~120 weekly observations is roughly one BTC cycle. Point estimates are wide.
- **Document every change in the new spec.** A "What changed from vN" section at the top of `strategy_v(N+1).md`, with the postmortem finding that motivated each change. Future-you needs the audit trail more than future-you needs another knob.
- **Prefer removing rules over adding them.** Our first postmortem already showed `no-sell` and `no-patience` both beat the baseline. Subtract before you add.
- **Frozen out-of-sample.** Before any tuning on iteration N, designate the most recent K weeks (suggest 20–26) as held-out. Don't look at them. Re-introduce only after the new spec is committed.
- **Spec changes only, no code changes for tuning.** If the spec says "20-week SMA" and the new spec says "26-week SMA", that's a spec change. Do not edit `analysis.py` to silently change parameters — every parameter that matters lives in the spec and is reflected in the report metadata.

## Naming convention

- Strategy specs are versioned: `strategy_v1.md`, `strategy_v2.md`, … Each is immutable once an analysis report has been produced from it.
- Specs live in `analysis/strategies/`. Scripts in `analysis/analysis_scripts/`. Reports in `analysis/results/`. Plots and CSVs in `analysis/output/`. See **Folder layout (enforced)** above.
- Every per-version artifact is suffixed `_vN`. Reports and outputs are committed per-version — they are **not** overwritten across runs. The whole point of keeping them is that each spec's record (what was claimed, what happened, what was diagnosed) stays available for context when writing the next spec.
- Baselines / control-account simulation logic lives in `common.py` and is shared across all version reports, so cross-version comparisons of the same benchmark are guaranteed identical by construction.

## What this loop is NOT

- Not online learning, not auto-tuning, not parameter search.
- Not a license to data-mine until something works in-sample.
- Not the dashboard. Live trading on the chameleon account follows the *current* committed spec; the research loop is offline work that produces the next spec.
