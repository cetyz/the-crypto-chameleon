# Research process

How we iterate on the chameleon's trading strategy. The point is to make every change deliberate and reviewable, not to chase backtest scores.

## The loop

```
  strategy_vN.md  ──►  analysis.py  ──►  analysis_report.md
                                              │
                                              ▼
                                        postmortem.py
                                              │
                                              ▼
                                       postmortem_report.md
                                              │
                                              ▼  (human reads, decides)
                                       strategy_v(N+1).md
```

One full lap = one strategy revision. No step is automated end-to-end — a human reads the postmortem and writes the next spec by hand.

## What each artifact is for

- **`analysis/strategy_vN.md`** — the spec we are *committing to* before we look at any results. Signals, policy table, overrides, action space, honest caveats. (Today's v1 lives at `analysis/placeholder_strat.md`.)
- **`analysis/analysis.py`** — runs the spec on cached data. Deterministic; same inputs → same outputs.
- **`analysis/analysis_report.md`** — headline numbers (return, max DD, Sharpe/Sortino, trade count, time-in-market, action distribution). Generated by `analysis.py`. The "what happened" artifact.
- **`analysis/postmortem.py`** → **`analysis/postmortem_report.md`** — the "why it happened" artifact. Per-policy-cell forward returns, counterfactual arms, signal-quality CIs, cash drag, regime breakdown.

## When to iterate

Concrete triggers for writing a new `strategy_v(N+1).md`:

1. A signal-state mean forward return has a 95% CI that **excludes zero in the opposite direction** to the spec's assumption. (E.g. "Hot" funding was supposed to be contrarian-bearish but its CI is firmly positive.)
2. A **counterfactual arm dominates** the baseline on both return and max DD. The component it strips out is a candidate for removal.
3. A policy cell has **n < 5** decisions in-sample — we cannot conclude anything about it; either change the spec so it fires more, or accept it as untested.
4. The **drawdown profile** is unacceptable for the dashboard's stated purpose (the win condition is risk-adjusted, not raw return — `placeholder_strat.md` is explicit about this).

If none of the above is true, do *not* iterate. Noise is not a signal.

## Discipline

- **Don't tune to in-sample noise.** ~120 weekly observations is roughly one BTC cycle. Point estimates are wide.
- **Document every change in the new spec.** A "What changed from vN" section at the top of `strategy_v(N+1).md`, with the postmortem finding that motivated each change. Future-you needs the audit trail more than future-you needs another knob.
- **Prefer removing rules over adding them.** Our first postmortem already showed `no-sell` and `no-patience` both beat the baseline. Subtract before you add.
- **Frozen out-of-sample.** Before any tuning on iteration N, designate the most recent K weeks (suggest 20–26) as held-out. Don't look at them. Re-introduce only after the new spec is committed.
- **Spec changes only, no code changes for tuning.** If the spec says "20-week SMA" and the new spec says "26-week SMA", that's a spec change. Do not edit `analysis.py` to silently change parameters — every parameter that matters lives in the spec and is reflected in the report metadata.

## Naming convention

- Strategy specs are versioned: `strategy_v1.md`, `strategy_v2.md`, … Each is immutable once an analysis report has been produced from it.
- Keep all historical specs in `analysis/`. Cheap to keep, very useful for context.
- `analysis_report.md` and `postmortem_report.md` get overwritten each run — they belong to the **current** spec only. If you need historical reports, commit them.

## What this loop is NOT

- Not online learning, not auto-tuning, not parameter search.
- Not a license to data-mine until something works in-sample.
- Not the dashboard. Live trading on the chameleon account follows the *current* committed spec; the research loop is offline work that produces the next spec.
